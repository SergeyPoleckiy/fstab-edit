# Техническое задание

## Программа для безопасного редактирования файла `/etc/fstab` в Linux

**Кодовое имя:** fstab-edit  
**Дата составления:** 18.11.2026  
**Версия ТЗ:** 2.0  
**Статус:** новая редакция ТЗ 1.0  

Исходный документ `fstab-editor.md` сохраняется без изменений. Настоящий документ является самостоятельной редакцией и заменяет ТЗ 1.0 как основу для разработки.

---

## 1. Общие сведения

### 1.1. Назначение программы

`fstab-edit` — утилита для безопасного и удобного редактирования файла `/etc/fstab` в Linux. Программа предоставляет CLI для автоматизации и TUI для интерактивной работы, сохраняет исходное форматирование и комментарии, проверяет файл-кандидат до записи, создаёт резервные копии и поддерживает откат изменений.

### 1.2. Основные принципы

1. Изменение файла выполняется как транзакция, а не как прямое перезаписывание.
2. Проверка файла и реальное монтирование являются разными операциями.
3. Неизменённые части файла сохраняются побайтово.
4. Ни одна запись не выполняется без успешно созданной и проверенной резервной копии.
5. Резервная копия гарантирует восстановление исходных байтов, но не гарантирует, что исходная конфигурация была работоспособной.
6. Неизвестные, но синтаксически допустимые возможности конкретной системы не отклоняются только потому, что они отсутствуют во встроенном списке программы.
7. Поведение CLI детерминировано и пригодно для неинтерактивного использования.
8. Программа не обещает невозможность любого повреждения системы; вместо этого определяются проверяемые гарантии записи, восстановления и диагностики сбоев.

### 1.3. Цели разработки

- Минимизировать риск повреждения системы при редактировании `/etc/fstab`.
- Упростить добавление и редактирование записей.
- Обеспечить автоматизацию через CLI и машиночитаемые форматы.
- Предоставить единый инструмент с CLI и TUI.
- Обеспечить восстановление после ошибок записи или проверки.
- Сохранять совместимость с различиями ядер, util-linux, файловых систем и mount helpers.

## 3. Технические требования

### 3.1. Язык и стек

- Язык: Go 1.22 или новее; точная версия toolchain фиксируется в проекте.
- CLI: `spf13/cobra`.
- TUI: `charmbracelet/bubbletea` или `rivo/tview`; выбор выполняется перед этапом 2.
- Конфигурация: YAML.
- Локализация: `go-i18n` или аналогичное решение.
- Основной артефакт: один статически слинкованный бинарный файл для `linux/amd64`.
- Сборка не должна требовать интерпретатор или динамические библиотеки приложения.

### 3.2. Внешние системные утилиты

Статическая сборка не означает отсутствие всех внешних зависимостей. Программа использует:

| Утилита | Назначение | Обязательность |
|---------|------------|----------------|
| `findmnt` | Статическая проверка и состояние монтирований | Обязательна для сохранения и `validate`/`verify-mount` |
| `blkid` | UUID, LABEL, PARTUUID, PARTLABEL и тип ФС | Необязательна; требуется функциям этапа 3 |
| `lsblk` | Дерево блочных устройств | Необязательна; требуется функциям этапа 3 |
| `mount` | Явное применение монтирований | Только для отдельной операции этапа 4 |
| mount helpers | CIFS, NFS, SSHFS и другие специфические типы | Зависят от используемой ФС |

Требования:

- В документации фиксируются минимальные проверенные версии утилит.
- При отсутствии необязательной утилиты связанные функции недоступны, остальные продолжают работать.
- При отсутствии `findmnt` запись системного файла запрещена; доступны операции, не требующие такой записи.
- Команды запускаются через `exec.CommandContext` или аналог без shell.
- Поиск исполняемых файлов выполняется только в доверенных системных каталогах; текущий каталог не используется.
- Для разбора вывода используются машиночитаемые режимы, если они доступны; иначе устанавливается `LC_ALL=C`.
- Для каждой команды задаются таймаут, отмена контекста и ограничение размера обрабатываемого вывода.
- Человекочитаемый вывод внешней утилиты не используется как стабильный программный API, если доступен машиночитаемый вариант.

### 3.3. Платформы

- Архитектура: `x86_64` (`amd64`).
- Минимальное ядро: Linux 5.x.
- Семейства дистрибутивов:
  - RHEL, Rocky, Alma, Fedora, CentOS Stream;
  - Debian, Ubuntu;
  - Arch Linux, Manjaro, EndeavourOS, CachyOS, Garuda Linux;
  - Astra Linux, РЕД ОС, ALT Linux.
- Поддерживаются конкретные версии ОС и util-linux из актуальной матрицы поддержки, а не семейство дистрибутивов в целом.
- Доступность типов ФС и опций определяется возможностями конкретной системы.

### 3.4. Архитектура

```text
cmd/          # Cobra-команды
internal/
  parser/     # Модель документа, разбор и сохранение исходного представления
  validator/  # Синтаксис, семантика, ошибки и предупреждения
  writer/     # Блокировки, контроль версии и атомарная запись
  backup/     # Резервные копии, метаданные, ротация и rollback
  config/     # YAML, окружение и приоритеты
  logger/     # Структурный журнал и ротация
  i18n/       # Русская и английская локализация
  sysutil/    # Безопасный запуск findmnt, blkid, lsblk и mount
pkg/
  models/     # Типы записей и результатов
tui/          # Интерактивный интерфейс
```

Бизнес-логика не должна зависеть от CLI или TUI. Оба интерфейса используют один транзакционный слой.

## 4. Модель и разбор `fstab`

### 4.1. Модель документа

Парсер работает с документом, а не только со списком записей. Модель должна сохранять:

- исходные байты каждой строки;
- переводы строк и их отсутствие в конце файла;
- пустые строки;
- обычные комментарии;
- закомментированные записи;
- позиции шести полей;
- исходное и декодированное значения полей;
- связанные блоки комментариев;
- хвостовой текст записи, если он присутствует.

Обязательное свойство: разбор и последующая сериализация неизменённого документа должны давать побайтово идентичный файл.

При изменении записи заменяются только соответствующие фрагменты. Остальные строки не выравниваются и не переформатируются.

### 4.2. Пробелы и экранирование

- Поля разделяются пробелами и табуляциями.
- Поддерживаются последовательности `\040`, `\011` и `\134`, а также другие формы, принимаемые используемой версией libmount/util-linux.
- JSON и другие структурированные выходные данные должны различать исходное и декодированное значение.
- Некорректные управляющие символы, NUL и неэкранированные переводы строк внутри поля являются ошибками.
- Поведение хвостовых комментариев проверяется совместимыми тестами с libmount/util-linux; независимо от интерпретации их исходный текст не должен теряться.

### 4.3. Комментарии

- Обычные комментарии не считаются записями.
- `comment` добавляет префикс `# ` к выбранной активной записи.
- `uncomment` снимает префикс только со строки, которая после этого разбирается как запись `fstab`.
- Произвольный текстовый комментарий не должен нечаянно превращаться в активную запись.
- Непрерывный блок непосредственно перед записью может считаться связанным комментарием; пустая строка разрывает связь.
- Редактирование связанного комментария не затрагивает заголовок файла и другие самостоятельные комментарии.
- Существующие комментарии и порядок строк сохраняются.

### 4.4. Поля записи

#### Поле 1 — устройство или ресурс

Поддерживаются:

- `UUID=<значение>`;
- `LABEL=<значение>`;
- `PARTUUID=<значение>`;
- `PARTLABEL=<значение>`;
- `/dev/sda1`, `/dev/nvme0n1p1`, `/dev/mapper/vg-lv` и другие пути;
- `//server/share` для CIFS;
- `server:/path` для NFS;
- `tmpfs`, `proc`, `sysfs`, `none` и другие допустимые источники.

Префикс идентификатора проверяется отдельно от значения. Формат UUID не ограничивается шаблоном `xxxx-xxxx`: длина и алфавит зависят от типа ФС.

#### Поле 2 — точка монтирования

- Для обычных записей используется абсолютный путь.
- Для `swap` допускается `none` в соответствии с практикой целевой системы.
- Пробелы и табуляции должны быть корректно экранированы.
- Дубликаты точек монтирования выдают предупреждение или ошибку по результатам совместимой проверки.
- Для `/`, `/boot`, `/boot/efi`, `/usr`, активных swap и других критичных записей выводится отдельное предупреждение.
- Программа не создаёт каталоги точек монтирования автоматически.

#### Поле 3 — тип файловой системы

Встроенный список подсказок включает:

- локальные: `ext2`, `ext3`, `ext4`, `xfs`, `btrfs`, `f2fs`, `reiserfs`;
- Windows-совместимые: `ntfs`, `ntfs3`, `ntfs-3g`, `vfat`, `exfat`, `msdos`;
- оптические: `iso9660`, `udf`;
- сетевые: `nfs`, `nfs4`, `cifs`, `sshfs`;
- псевдо-ФС и специальные: `tmpfs`, `proc`, `sysfs`, `devpts`, `swap`, `overlay`, `auto`, `none`.

Особые правила:

- `bind` является опцией монтирования, а не типом ФС; типичная запись использует тип `none`.
- `smbfs` не входит в список рекомендуемых типов; существующая запись сохраняется и получает предупреждение о возможной устаревшести.
- Встроенный список предназначен для подсказок, а не является исчерпывающим белым списком.
- Неизвестный тип допускается на синтаксическом уровне и сопровождается предупреждением; доступность проверяется средствами системы.

#### Поле 4 — опции монтирования

- Проверяются разделители, пустые элементы и недопустимые неэкранированные пробелы.
- Учитываются общие и FS-специфические опции, включая `defaults`, `noatime`, `nofail`, `ro`, `rw`, `user`, `auto`, `noauto`, `exec`, `noexec`, `sync`, `async`, `relatime`, `nodev`, `nosuid`, `bind`, `_netdev` и `x-systemd.*`.
- Обнаруживаются повторы и очевидные конфликты, например `ro,rw` или `auto,noauto`; учитывается приоритет последней опции там, где это определено системой.
- Неизвестная опция вызывает предупреждение, а не автоматическую ошибку.
- Строгие отказы допускаются только для однозначно некорректного синтаксиса или подтверждённой несовместимости.
- Секретные значения опций не должны попадать в журнал без маскирования.

#### Поля 5 и 6 — Dump и Pass

- Синтаксически значение должно быть неотрицательным десятичным целым в поддерживаемом целевыми утилитами диапазоне.
- Типичные значения `dump`: `0` и `1`.
- Типичные значения `pass`: `0`, `1` и `2`.
- Другие неотрицательные значения не объявляются автоматически синтаксической ошибкой; выдаётся предупреждение с учётом поведения `dump`, `fsck` и util-linux.
- Отсутствие необязательных полей сохраняется; при создании новой записи по умолчанию выводятся все шесть полей.

## 5. Валидация

### 5.1. Уровни результатов

- **Ошибка:** документ невозможно корректно разобрать либо операция однозначно создаёт недопустимую запись.
- **Предупреждение:** конфигурация потенциально опасна или зависит от окружения, но не является однозначно некорректной.
- **Информация:** пояснение о нестандартной, устаревшей или автоматически скорректированной настройке.

Каждый результат содержит стабильный машиночитаемый код, строку, поле, локализованное сообщение и, где применимо, исходное значение.

### 5.2. Виды проверок

- Структура документа и шести полей.
- Экранирование и разделители.
- Типичные значения `dump` и `pass`.
- Дубликаты устройств и точек монтирования.
- Существование устройства и точки монтирования как проверки окружения.
- Доступность типа ФС и mount helper.
- Общие и специфические опции.
- Специальные правила для swap, network, `noauto`, `nofail`, `_netdev` и bind.
- Статическая проверка через `findmnt --verify --tab-file`.

Отсутствие съёмного или сетевого устройства не должно автоматически считаться повреждением файла. Для записей с `noauto` или `nofail` такая ситуация обычно является предупреждением.

### 5.3. Онлайн- и офлайн-проверка

- Стандартный режим проверяет как файл, так и доступное окружение.
- Флаг `--offline` отключает требования к фактическому наличию устройств, сетевых ресурсов и mount helpers, но не отключает разбор и синтаксическую проверку.
- `findmnt --verify` остаётся обязательным перед обычным сохранением.
- Предупреждения не считаются ошибкой только на основании ненулевого кода внешней команды без анализа результата; классификация должна быть определена и покрыта тестами.

### 5.4. Реальное монтирование

`mount -a` не используется как обязательная проверка перед или после сохранения.

Отдельная команда `apply-mounts` на этапе 4:

- явно запрашивается пользователем;
- требует подтверждения и необходимых привилегий;
- использует зафиксированный снимок проверенного файла;
- имеет таймаут и подробный результат;
- сообщает, что монтирование могло завершиться частично;
- не утверждает, что откат файла отменяет уже выполненные монтирования;
- не выполняет автоматическое размонтирование без отдельного явного требования.

Записи с `noauto`, уже смонтированные ФС, сетевые ресурсы и загрузочные сценарии требуют отдельных тестов и не считаются доказанными одним запуском `mount -a`.

## 6. Блокировки и транзакционная запись

### 6.1. Блокировка

- Для изменений используется отдельный стабильный lock-файл, а не inode самого `/etc/fstab`.
- Для системного файла каталог по умолчанию: `/run/lock/fstab-edit/`.
- Для непривилегированной работы с `--file` используется `$XDG_RUNTIME_DIR/fstab-edit/` либо другой безопасный пользовательский runtime-каталог.
- Имя lock-файла содержит SHA-256 канонического абсолютного пути целевого файла.
- Каталог и lock-файл создаются с ограниченными правами.
- Эксклюзивная блокировка удерживается на всю критическую последовательность чтения, проверки, backup, записи, повторной проверки и возможного rollback.
- TUI не удерживает блокировку всю сессию; блокировка берётся при сохранении.
- `flock` не заменяет проверку версии, поскольку сторонние программы могут не соблюдать блокировку.

### 6.2. Контроль внешних изменений

- При загрузке файла вычисляется SHA-256 исходного содержимого.
- Перед записью под блокировкой файл читается повторно.
- Если хеш отличается от версии, на которой основаны изменения, запись запрещается.
- TUI предлагает просмотреть конфликт и повторно загрузить файл; автоматического перезаписывания нет.
- В CLI ситуация завершается отдельным кодом ошибки конфликта.

### 6.3. Последовательность сохранения

1. Построить документ-кандидат в памяти.
2. Выполнить собственный разбор и проверки.
3. Получить эксклюзивную блокировку.
4. Повторно прочитать оригинал и проверить базовый хеш.
5. Создать безопасный временный файл-кандидат.
6. Выполнить `findmnt --verify --tab-file <candidate>` и классифицировать результат.
7. Проверить доступность обязательного журнала до точки изменения.
8. Создать резервную копию исходного файла и её метаданные.
9. Выполнить `fsync` резервной копии и метаданных и проверить их чтением и SHA-256.
10. Создать финальный временный файл в каталоге целевого файла.
11. Сохранить владельца, режим, необходимые расширенные атрибуты и SELinux-контекст.
12. Выполнить `fsync` временного файла.
13. Атомарно заменить целевой файл через `rename`.
14. Выполнить `fsync` родительского каталога.
15. Повторно прочитать записанный файл, проверить ожидаемый хеш и выполнить `findmnt --verify --tab-file <target>`.
16. При ошибке после замены автоматически восстановить резервную копию текущей транзакции.
17. Записать результат в журнал и освободить блокировку.

Временные файлы создаются с безопасными правами, без следования символическим ссылкам и удаляются при штатном завершении.

### 6.4. Тип целевого файла

- Целевой файл должен быть обычным файлом.
- Символические ссылки, каталоги, сокеты, FIFO и устройства отклоняются.
- Родительский каталог и пути резервных копий проверяются на небезопасную подмену.
- Если безопасный контекст или владелец не могут быть сохранены, замена системного файла не выполняется.

### 6.5. SELinux и AppArmor

- Программа не создаёт и не изменяет политики SELinux/AppArmor.
- Root не считается обходом мандатного контроля доступа.
- Отказ `EACCES`/`EPERM` отображается как ошибка среды с диагностикой.
- При записи сохраняются доступные security xattrs и контекст оригинала.
- Проверки выполняются как минимум в одной среде SELinux enforcing в матрице релизных испытаний.

### 6.6. Dry run

`--dry-run`:

- не изменяет целевой файл;
- не создаёт и не ротирует резервные копии;
- не пишет файловый журнал;
- допускает временные файлы в приватном каталоге для проверки и удаляет их;
- показывает unified diff либо структурированное представление изменений;
- выполняет только read-only проверки окружения.

## 7. Резервное копирование и откат

### 7.1. Создание копии

- Каталог по умолчанию: рядом с оригиналом.
- Переопределение: `--backup-dir` или `backup.dir`.
- Имя по умолчанию: `fstab.bak.<backup-id>`.
- `backup-id` формируется в UTC с наносекундами:

```text
YYYY-MM-DD_HH-MM-SS.nnnnnnnnnZ
```

Пример:

```text
fstab.bak.2026-11-18_15-30-45.123456789Z
```

- При коллизии добавляется числовой суффикс; создание выполняется атомарно с `O_EXCL`.
- Копия создаётся до каждой реальной записи целевого файла.
- Ручная команда `backup` также создаёт копию и метаданные.
- Файл копии создаётся с режимом `0600`; исходные права и владелец сохраняются в метаданных для восстановления.

### 7.2. Метаданные

Для каждой новой копии создаётся sidecar-файл с версией схемы и полями:

- идентификатор копии;
- время в UTC;
- канонический путь источника;
- SHA-256 содержимого;
- исходные UID, GID и режим;
- операция (`before-add`, `before-edit`, `before-delete`, `before-comment`, `before-uncomment`, `before-rollback`, `manual`);
- версия программы;
- результат доступной проверки исходника.

Метаданные не изменяют содержимое самой копии.

### 7.3. Ротация

- По умолчанию хранятся последние 10 копий для конкретного целевого файла и префикса.
- Ротация запускается только после полностью завершённой операции.
- Удаляются только файлы, однозначно распознанные как собственные копии программы.
- Чужие файлы, символические ссылки и копии другого целевого файла не удаляются.
- Копия, выбранная для текущего rollback, и копии незавершённой либо аварийной операции не удаляются.
- Пользовательские файлы с похожим именем не включаются в ротацию без корректных метаданных.

### 7.4. Ручной rollback

`fstab-edit rollback` выбирает последнюю подходящую копию текущего целевого файла. `fstab-edit rollback --restore=<backup-id>` выбирает конкретную копию.

Последовательность:

1. Найти и запомнить целевую копию **до** создания страховочной копии текущего состояния.
2. Проверить принадлежность копии текущему целевому файлу, её SHA-256 и метаданные.
3. Показать diff и получить подтверждение.
4. Создать страховочную копию текущего состояния.
5. Восстановить выбранную копию через тот же атомарный writer.
6. Выполнить повторную проверку и сообщить результат.

Это исключает ситуацию, при которой «последней копией» становится только что созданная копия неизменённого текущего состояния и rollback становится пустой операцией.

### 7.5. Автоматический rollback

- Используется строго копия, созданная перед текущей транзакцией, а не повторный поиск последней копии.
- Выполняется одинаково в CLI и TUI.
- TUI показывает ошибку и результат rollback, но не предлагает молча оставить не прошедший проверку файл.
- Целостность копии проверяется до восстановления.
- Семантическая проверка исходной копии выполняется и сообщается, но не подменяет требование восстановить исходное состояние после неудачной транзакции.
- Если rollback также завершился ошибкой, программа возвращает отдельный критический код, выводит пути к исходной копии, текущему файлу и журналу и не пытается бесконечно повторять запись.

### 7.6. Сухой rollback

`rollback --dry-run` выбирает и проверяет копию и показывает diff без создания страховочной копии, ротации, записи файла или журнала.

## 8. CLI

### 8.1. Команды

```bash
fstab-edit list
fstab-edit add [флаги]
fstab-edit edit <id> [флаги]
fstab-edit delete <id>
fstab-edit comment <id>
fstab-edit uncomment <id>
fstab-edit validate
fstab-edit verify-mount
fstab-edit backup
fstab-edit rollback [--restore=<backup-id>]
fstab-edit apply-mounts             # этап 4
fstab-edit tui                      # этап 2
```

`verify-mount` выполняет статическую проверку указанного файла через `findmnt --verify` и не монтирует ресурсы.

До появления TUI запуск без аргументов показывает справку. Начиная с этапа 2 запуск без аргументов открывает TUI; `--help` всегда показывает справку.

### 8.2. Идентификация записей

Краткая форма `<id>` поддерживает:

- физический номер строки, начиная с 1;
- точку монтирования;
- устройство или ресурс.

Физический номер строки учитывает все строки, включая пустые и комментарии. Для активных операций строка должна содержать запись подходящего состояния.

Для скриптов предпочтительны явные селекторы:

```text
--line <n>
--mount-point <path>
--device <source>
```

Правила:

- Совпадение выполняется по полному декодированному значению, а не по подстроке.
- Символические ссылки в точке монтирования не разрешаются для определения идентичности записи.
- Дубликаты приводят к неоднозначности.
- Интерактивный выбор предлагается только при наличии TTY и отсутствии `--yes`.
- В неинтерактивном режиме неоднозначность завершает команду отдельным кодом и выводит список кандидатов.
- `--yes` подтверждает операцию, но не выбирает произвольный кандидат и не снимает неоднозначность.

### 8.3. Глобальные флаги

| Флаг | Назначение |
|------|------------|
| `--file=<path>` | Альтернативный путь к fstab |
| `--dry-run` | Показать изменения без записи |
| `--yes`, `-y` | Автоподтверждение допустимых операций |
| `--output=<format>`, `-o` | `table`, `json`, `csv`, `tsv` |
| `--log-level=<level>` | `debug`, `info`, `warn`, `error` |
| `--verbose`, `-v` | Дополнительная диагностика |
| `--quiet`, `-q` | Подавление обычного stdout-вывода |
| `--backup-dir=<path>` | Каталог резервных копий |
| `--offline` | Не требовать наличия внешних устройств и helpers |
| `--lang=ru|en` | Язык сообщений |
| `--config=<path>` | Явный путь конфигурации |
| `--help`, `-h` | Справка |
| `--version` | Версия программы |

`--verbose` и `--quiet` взаимоисключающие. Ошибки не скрываются `--quiet`. Данные выводятся в stdout, диагностика — в stderr, если выбранный машиночитаемый протокол не определяет иное явно.

### 8.4. Флаги добавления и редактирования

```text
--device <source>
--mount <path>
--type <fstype>
--options <list>
--dump <n>
--pass <n>
--comment <text>
--clear-comment
--unset-dump
--unset-pass
```

При `add` обязательны устройство, точка монтирования, тип и опции; отсутствующие `dump`/`pass` получают документированные значения по умолчанию. При `edit` меняются только явно переданные поля. Пустое обязательное поле запрещено.

### 8.5. Машиночитаемый вывод

- JSON содержит `schema_version`.
- Записи содержат физический номер строки, состояние, шесть исходных и декодированных полей, связанный комментарий и результаты проверки.
- Схема JSON версионируется; обратно несовместимые изменения требуют новой версии схемы.
- CSV/TSV используют корректное quoting/escaping и не смешиваются с диагностикой.
- Цветной вывод отключён для машиночитаемых форматов.
- Локализация не меняет коды ошибок и имена полей.

### 8.6. Коды выхода

| Код | Значение |
|-----|----------|
| 0 | Успешно; допустимы предупреждения |
| 1 | Проверка завершилась ошибкой |
| 2 | Ошибка аргументов CLI |
| 3 | Недостаточно прав |
| 4 | Блокировка или конфликт версии файла |
| 5 | Ошибка или таймаут внешней утилиты |
| 6 | Ошибка ввода-вывода, backup или записи |
| 7 | Критический сбой rollback |
| 8 | Неоднозначный идентификатор записи |

### 8.7. Подтверждения

Подтверждение `[y/N]` требуется для `add`, `edit`, `delete`, `comment`, `uncomment`, `rollback` и `apply-mounts`.

- Без TTY изменяющая команда требует `--yes`.
- Перед подтверждением показывается diff.
- Для критичных записей выводится дополнительное предупреждение, но одно `--yes` является явным подтверждением всей запрошенной операции.
- Неоднозначность, ошибка валидации и конфликт версии не обходятся флагом `--yes`.

### 8.8. Примеры

```bash
fstab-edit list
fstab-edit list -o json

fstab-edit add --device UUID=abc-123 --mount /mnt/data --type ext4 \
  --options defaults,noatime --dump 0 --pass 2

fstab-edit edit --mount-point /mnt/data --options defaults,noatime,nofail
fstab-edit delete --mount-point /mnt/data --yes

fstab-edit validate --file ./fstab.test --offline
fstab-edit verify-mount --file ./fstab.test

fstab-edit rollback
fstab-edit rollback --restore=2026-11-18_15-30-45.123456789Z
fstab-edit rollback --dry-run
```

## 9. TUI — этап 2

### 9.1. Основной экран

```text
┌─ fstab-edit ──────────────────────────────────────────────────┐
│ # │ Device          │ Mount    │ Type │ Options    │ D │ P │ ✓│
│───┼─────────────────┼──────────┼──────┼────────────┼───┼───┼──│
│ 1 │ UUID=abc-123... │ /        │ ext4 │ defaults   │ 0 │ 1 │ ✓│
│ 2 │ UUID=def-456... │ /home    │ ext4 │ defaults   │ 0 │ 2 │ ✓│
│ 3 │ /dev/sdb1       │ /mnt/usb │ vfat │ noauto,user│ 0 │ 0 │ -│
│                                                               │
│ [Enter] Edit  [Ins] Add  [Del] Delete  [F1] Help  [F10] Quit  │
└───────────────────────────────────────────────────────────────┘
```

Отображаются активные и закомментированные записи, состояние проверки и признак несохранённых изменений. Обычные комментарии доступны через просмотр документа или связанную запись.

### 9.2. Модель изменений

- Изменения накапливаются в памяти до сохранения.
- `Ctrl+Z` отменяет только последнее несохранённое действие.
- После сохранения используется отдельная операция rollback.
- `Ctrl+S` и `F2` запускают одну транзакцию сохранения.
- При сохранении применяются общие блокировка, контроль хеша, backup, атомарная запись, проверка и rollback.
- При конфликте версии TUI не перезаписывает файл и предлагает diff/повторную загрузку.
- `F5` при наличии несохранённых изменений запрашивает подтверждение перед перезагрузкой.
- `Ctrl+Q`, `F10` и закрытие приложения запрашивают подтверждение при наличии несохранённых изменений.
- После неуспешной проверки TUI показывает результат автоматического rollback и не предлагает оставить не прошедший проверку файл как обычный вариант.

### 9.3. Управление

- Только клавиатура; мышь не требуется.
- Стрелки, Enter, Esc, Del, Tab.
- `Ctrl+S` — сохранить.
- `Ctrl+Q` — выйти.
- `Ctrl+Z` — отменить несохранённое действие.
- `F1` — помощь.
- `F2` — сохранить.
- `F5` — обновить.
- `F10` — выйти.

### 9.4. Формы

- Добавление и редактирование шести полей и связанного комментария.
- Проверка полей при вводе без изменения файла.
- Предпросмотр итоговой строки и полного diff.
- Подсветка полей, ошибок, предупреждений и информационных сообщений.
- Ошибки не опираются только на цвет: добавляются текстовые обозначения.

- На этапе 4: `light`, `high-contrast` и пользовательские темы через конфигурацию.
- Во всех темах сохраняются текстовые признаки ошибок и предупреждений.

## 10. Автодополнение и блочные устройства — этап 3

### 10.1. Автодополнение

- Контекстно-зависимые подсказки опций по типу ФС.
- Подсказки не превращаются в запрет неизвестных опций.
- Учитываются общие опции, `x-systemd.*`, `_netdev`, bind, network и swap.
- Источник подсказок версионируется отдельно от правил обязательной валидации.
- Пользователь может вручную ввести значение, отсутствующее в подсказках.

### 10.2. Обнаружение устройств

- `lsblk` используется предпочтительно в JSON-режиме с явным списком полей и размерами в байтах.
- `blkid` используется для UUID, LABEL, PARTUUID, PARTLABEL и типа ФС.
- Вывод не разбирается по локализованным человекочитаемым колонкам.
- Отображаются holders, дочерние устройства, точки монтирования и swap, чтобы уменьшить риск ошибочного выбора.
- Недоступность устройства или недостаток прав отображается отдельно от пустого списка.

### 10.3. Автоподстановка идентификаторов

- Автоподстановка выполняется только по явному выбору пользователя либо отдельному флагу; исходный путь не заменяется незаметно.
- Пользователь выбирает предпочтительный тип: UUID, PARTUUID, LABEL, PARTLABEL или сохранение исходного пути.
- Если идентификатор отсутствует или неоднозначен, программа сообщает об этом и не выбирает произвольное устройство.
- LABEL и PARTLABEL проверяются на дубликаты.
- Сетевые ресурсы и псевдо-ФС не передаются в `blkid` как блочные устройства.

## 11. Права, конфигурация и журналирование

### 11.1. Права

- `list`, `validate`, `verify-mount`, `backup --dry-run` и другие read-only операции не требуют root сами по себе.
- Изменение `/etc/fstab` требует effective UID 0.
- Работа с альтернативным `--file` выполняется с правами текущего пользователя; root требуется только если его требуют фактические права или операция.
- Недостаток прав для `blkid`, устройства или каталога отображается отдельно.
- Подсказка о `sudo` выводится только когда повышение прав действительно необходимо.
- Read-only команды не создают `/var/log/fstab-edit.log` и другие административные файлы.

### 11.2. Источники конфигурации

Приоритет от высшего к низшему:

1. Флаги CLI.
2. Переменные окружения `FSTAB_EDIT_*`.
3. Пользовательский YAML.
4. Системный YAML.
5. Встроенные значения по умолчанию.

YAML-файлы объединяются по ключам; не заданные ключи сохраняют значение более низкого уровня.

Пути:

```text
/etc/fstab-edit/config.yaml
~/.config/fstab-edit/config.yaml
```

Для root домашний каталог определяется по записи пользователя effective UID, а не по непроверенному `HOME`. Конфигурация непривилегированного `SUDO_USER` автоматически не загружается root-процессом.

### 11.3. Безопасность конфигурации

- Символические ссылки на конфигурацию отклоняются.
- Root отклоняет пользовательские конфигурации, не принадлежащие root либо доступные группе/остальным на запись.
- Системная конфигурация должна принадлежать root и не быть доступной непривилегированным пользователям на запись.
- `--config` задаёт файл явно, но проверки владельца и прав сохраняются.
- Небезопасная конфигурация не игнорируется молча: выводится ошибка.

### 11.4. Пример конфигурации

```yaml
fstab_path: /etc/fstab

backup:
  dir: /etc
  prefix: fstab.bak
  keep: 10

log:
  file: /var/log/fstab-edit.log
  level: info
  max_size_mb: 10
  keep: 5

tui:
  theme: dark
```

### 11.5. Журнал

- По умолчанию: `/var/log/fstab-edit.log`.
- Формат: структурированный JSON Lines, по одной записи на событие.
- Коды событий и операций не локализуются; человекочитаемое сообщение может локализоваться отдельно.
- Каждая запись содержит timestamp ISO 8601, уровень, реальный и effective UID, доступные проверенные сведения о sudo, операцию, целевой файл, backup-id, результат и код ошибки.
- Для изменений сохраняются старое и новое значения с экранированием переводов строк.
- Опции и URL, содержащие пароли, токены или другие секреты, маскируются.
- По умолчанию используются ротация при 10 МиБ и пять архивных файлов.
- Журнал не пишется в systemd journal в базовой версии.
- Для изменяющей команды доступность журнала проверяется до записи целевого файла; если журнал недоступен до точки изменения, операция не начинается.
- Сбой журнала после замены файла не должен помешать обязательному rollback; пользователь получает критическую диагностику обоих событий.

## 14. Тестирование

### 14.1. Виды тестов

- Unit: parser, validator, writer, backup, config, logger и адаптеры внешних утилит.
- Golden: известные входные файлы и ожидаемые изменения.
- Round-trip: неизменённый документ сохраняется побайтово.
- Fuzz: parser, экранирование, разделители и комментарии.
- Integration: реальные операции с временным `fstab` от обычного пользователя, где это возможно.
- E2E CLI: stdout, stderr, JSON-схема и коды выхода.
- TUI: `teatest` либо expect-подобные тесты начиная с этапа 2.
- Privileged: mount, SELinux, загрузка и реальные устройства только в изолированных VM.

### 14.2. Обязательные сценарии безопасности

- Невозможность получить блокировку.
- Внешнее изменение файла после загрузки.
- Нехватка места и read-only ФС.
- Сбой создания backup или metadata.
- Несовпадение SHA-256 backup.
- Сбой до и после `rename`.
- Сбой `fsync`, если он моделируется используемой тестовой средой.
- Таймаут и ненулевой выход `findmnt`.
- Сбой повторной проверки записанного файла.
- Успешный rollback после каждой допустимой точки сбоя.
- Двойной сбой записи и rollback с критической диагностикой.
- Подмена target, backup, metadata, config и log символическими ссылками.
- Сохранение владельца, прав и доступных security xattrs.
- Ротация без удаления чужих и используемых копий.
- Выбор цели rollback до создания страховочной копии.
- Частичное выполнение `apply-mounts` на этапе 4 без ложного заявления об откате состояния.

### 14.3. Загрузочные испытания

Контейнеры используются для parser/CLI-тестов, но не считаются доказательством загрузки системы.

В изолированных VM проверяются:

- изменение корневой записи;
- `/boot` и `/boot/efi`;
- отдельный `/home`;
- swap;
- `nofail`, `noauto`, `_netdev` и bind;
- восстановление после намеренно неуспешной транзакции;
- фактическая перезагрузка после принятых изменений;
- SELinux enforcing хотя бы в одной поддерживаемой среде.

Релизная матрица содержит конкретные версии ОС и util-linux. QEMU/VM используются для загрузочных сценариев; контейнеры не подменяют их.

### 14.4. Покрытие

- Общее покрытие не ниже 80%.
- Покрытие не заменяет обязательные сценарии отказов.
- Критические пути parser, writer, backup и rollback должны быть покрыты поведенческими тестами независимо от достигнутого общего процента.

## 15. Этапы разработки

Разработка делится ровно на четыре этапа. Каждый этап завершается работающим бинарником, тестами и обновлённой документацией.

### Этап 1 — ядро и CLI

Входит:

- модель документа и побайтово сохраняющий parser;
- шесть полей, комментарии и экранирование;
- ошибки, предупреждения и информационные сообщения;
- статическая валидация через `findmnt --verify --tab-file`;
- стабильные lock-файлы и контроль SHA-256 базовой версии;
- атомарная запись, права, владелец и security context;
- backup, metadata, ротация, ручной и автоматический rollback;
- все основные CLI-команды: `list`, `add`, `edit`, `delete`, `comment`, `uncomment`, `validate`, `verify-mount`, `backup`, `rollback`;
- `--file`, `--dry-run`, `--yes`, явные селекторы, `--offline`;
- table/JSON/CSV/TSV, коды выхода и подтверждения;
- конфигурация, журнал, RU/EN;
- unit, golden, round-trip, fuzz, integration и CLI E2E;
- README, Markdown-руководство, man, примеры, CHANGELOG и документация разработчика;
- CI, сборка и SHA-256;
- базовые VM-тесты транзакций и загрузки.

Не входит: TUI, обнаружение блочных устройств, автоматическая подстановка UUID/LABEL, контекстное автодополнение, PDF и `apply-mounts`.

Критерий завершения: все основные операции доступны через CLI, а сценарии сбоя не оставляют программу без диагностики и выполняют заданный rollback.

### Этап 2 — TUI

Входит:

- основной экран и таблица активных/закомментированных записей;
- формы добавления и редактирования;
- несохранённое состояние, undo до сохранения и dirty-индикатор;
- сохранение через транзакционное ядро этапа 1;
- обработка конфликтов версии и автоматический rollback;
- просмотр diff;
- статус монтирований через `findmnt`;
- история backup, diff и восстановление;
- журнал операций и помощь;
- клавиатурное управление;
- темы `dark` и `monochrome`;
- TUI-тесты и обновлённая документация;
- запуск TUI командой `tui` и запуском без аргументов.

Критерий завершения: все операции этапа 1 доступны из TUI без отдельной небезопасной реализации записи.

### Этап 3 — автодополнение, блочные устройства и PDF

Входит:

- контекстное автодополнение опций;
- экран блочных устройств;
- интеграция `lsblk` и `blkid`;
- выбор устройства в формах;
- явная автоподстановка UUID, PARTUUID, LABEL и PARTLABEL;
- обработка отсутствующих и повторяющихся идентификаторов;
- тесты машиночитаемого вывода и недоступности утилит;
- генерация PDF из Markdown-руководства;
- обновление CLI/TUI/help и release-артефактов.

Критерий завершения: пользователь может выбрать обнаруженное устройство и получить идентификатор без ручного запуска `blkid`, а PDF соответствует актуальному Markdown-руководству.

### Этап 4 — всё остальное

Входит:

- `apply-mounts` как отдельная явная операция с таймаутом и отчётом о частичном выполнении;
- дополнительные FS- и helper-специфические подсказки;
- расширенная поддержка сетевых и специальных сценариев;
- темы `light`, `high-contrast` и пользовательские темы;
- дополнительные диагностические экраны;
- расширенная матрица QEMU/VM и SELinux-тестов;
- оставшиеся улучшения UX, документации, совместимости и CI;
- финальные ручные приёмочные испытания всех заявленных версий ОС.

Критерий завершения: выполнены все требования настоящего ТЗ и финальные критерии приёмки без абсолютных и недоказуемых гарантий.

## 16. Финальные критерии приёмки

Программа готова к полному релизу, если:

1. Завершены все четыре этапа.
2. Неизменённый документ проходит побайтовый round-trip.
3. Изменение одной записи не переформатирует остальные строки.
4. Все основные операции доступны в CLI и TUI, кроме функций, по смыслу привязанных к одному интерфейсу.
5. Перед каждой записью создаётся и проверяется восстановимая копия.
6. Запись выполняется атомарно и с контролем внешних изменений.
7. Неуспешная повторная проверка вызывает rollback конкретной копии транзакции в CLI и TUI.
8. Двойной сбой записи и rollback выдаёт критический код и точные пути для ручного восстановления.
9. Реальное монтирование не используется как скрытая часть сохранения файла.
10. Все обязательные сценарии раздела 14 покрыты тестами.
11. Общее покрытие не ниже 80%, CI и линтер успешны.
12. Подготовлены RU/EN, Markdown, PDF, man, README, CHANGELOG и документация разработчика.
13. Выпущены статический бинарник `linux/amd64`, документация и SHA-256.
14. Проведены VM-испытания конкретных поддерживаемых версий Debian-, RHEL-, Arch-семейств, Astra Linux, РЕД ОС и ALT Linux.
15. Выполнены заявленные загрузочные сценарии и тест SELinux enforcing.

Не используется критерий «доказана невозможность окирпичивания». Проверяются конкретные свойства транзакций, восстановления, диагностики и загрузки в поддерживаемых сценариях.

## 17. Риски и ограничения

| Риск | Меры |
|------|------|
| Некорректный `fstab` препятствует загрузке | Проверка candidate, backup, атомарная запись, rollback и VM reboot-тесты |
| Исходный файл уже повреждён | Копия гарантирует восстановление байтов, но не объявляется работоспособной |
| Сторонняя программа игнорирует `flock` | Контроль SHA-256 и отказ от перезаписи |
| Атомарная замена меняет inode | Отдельный стабильный lock-файл |
| `mount -a` частично меняет систему | Отдельная явная операция, таймаут и отчёт; нет ложного обещания отката монтирований |
| Различия util-linux и mount helpers | Адаптеры, машиночитаемый вывод, версии в матрице поддержки |
| Неизвестные новые опции | Предупреждение вместо автоматического запрета |
| Потеря SELinux-контекста | Сохранение xattrs/context и enforcing-тесты |
| Небезопасный config/backup/log | Проверка владельца, прав, типов файлов и symlink-атак |
| Секреты в опциях | Маскирование структурированного журнала |
| Сбой самого rollback | Отдельный код 7, сохранение копий и инструкции ручного восстановления |
| Контейнер не проверяет загрузку | Изолированные QEMU/VM с фактической перезагрузкой |
