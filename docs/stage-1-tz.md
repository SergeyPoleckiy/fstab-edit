## 1. Назначение и результат этапа

Цель первого этапа — создать безопасное ядро редактирования `fstab` и полноценный CLI без TUI.

К завершению этапа должна существовать статически слинкованная программа `fstab-edit` для `linux/amd64`, которая:

- читает активные и закомментированные записи;
- добавляет, редактирует, удаляет, комментирует и раскомментирует записи;
- сохраняет неизменённые части документа побайтово;
- выполняет внутреннюю проверку и `findmnt --verify`;
- использует отдельный lock-файл и контроль SHA-256 базовой версии;
- создаёт резервные копии с метаданными;
- выполняет атомарную запись;
- автоматически откатывает неуспешную транзакцию;
- поддерживает ручной backup и rollback;
- предоставляет table, JSON, CSV и TSV;
- поддерживает RU/EN, YAML, переменные окружения и структурный журнал;
- имеет автоматические тесты, документацию и CI.

Первый этап должен давать самостоятельно полезный продукт, а не только заготовку архитектуры.

## 3. Базовые ограничения

- Язык: Go 1.22 или новее; версия toolchain фиксируется в `go.mod`/CI.
- CLI: `spf13/cobra`.
- Целевая ОС: Linux.
- Release-архитектура: `amd64`.
- Минимальное ядро: Linux 5.x.
- Основной бинарник должен собираться статически, ориентир сборки: `CGO_ENABLED=0`.
- Целевой файл по умолчанию: `/etc/fstab`.
- Альтернативный файл задаётся глобальным `--file` или `fstab_path`.
- Для сохранения обязателен `findmnt` с поддержкой `--verify` и `--tab-file`.
- Реальное монтирование не является частью сохранения.
- Любая запись выполняется только через общий транзакционный слой.
- Никакие тесты не должны изменять реальный `/etc/fstab` машины разработчика или CI-runner.

## 4. Архитектура и границы компонентов

```text
cmd/                  # Cobra-команды, аргументы, prompts и представление результата
internal/
  parser/             # Документ, строки, записи, raw spans, decode/encode
  validator/          # Внутренние проверки и классификация findmnt
  writer/             # Lock, base hash, transaction, atomic replace, rollback
  backup/             # Создание, metadata, выбор, verify и rotation
  config/             # Defaults, YAML, env и CLI overrides
  logger/             # JSON Lines, rotation и redaction
  i18n/               # Каталоги RU/EN и выбор языка
  sysutil/            # Поиск и запуск findmnt без shell
pkg/
  models/             # Экспортируемые модели записей и результатов
docs/                 # Пользовательская и разработческая документация
examples/             # Примеры YAML и fstab
```

### 4.1. Правила зависимостей

- `parser` не зависит от CLI, внешних команд и прав доступа.
- `validator` получает данные окружения через интерфейсы и не запускает процессы напрямую.
- `backup` не изменяет целевой `fstab`.
- Низкоуровневый writer выполняет атомарную замену, но не выбирает резервную копию самостоятельно.
- Оркестрация транзакции находится в доменном слое, а не в обработчиках Cobra.
- CLI только преобразует аргументы в доменную операцию и отображает результат.
- Внешние команды и файловые операции, требующие fault injection, скрыты за интерфейсами.
- Локализованные сообщения не используются как признак типа ошибки в бизнес-логике.

### 4.2. Минимальные доменные модели

Конкретные имена Go-типов могут уточняться в реализации, но модели должны выражать:

- документ как упорядоченную последовательность узлов;
- активную запись;
- закомментированную запись;
- обычный комментарий;
- пустую строку;
- исходный текст и line ending каждого узла;
- исходные позиции изменяемых полей;
- физический номер строки;
- результат проверки с severity и стабильным кодом;
- base SHA-256 документа;
- backup metadata;
- результат транзакции и rollback.

### 4.3. Требования к максимальному комментированию файлов

Все файлы проекта должны быть **максимально содержательно прокомментированы на русском языке**. Это обязательное требование, а не рекомендация.

#### Исходный код Go

- Каждый файл должен содержать пояснение его назначения, основных обязанностей и места в архитектуре.
- Каждый пакет должен иметь русский package comment с описанием ответственности, основных инвариантов и границ использования.
- Комментируются экспортируемые и неэкспортируемые типы, функции, методы, константы и неочевидные поля структур.
- Для функций описываются назначение, параметры, возвращаемые значения, ошибки, побочные эффекты, требования к правам и внешним ресурсам.
- Для интерфейсов описывается контракт каждого метода, ожидаемые реализации и требования к потокобезопасности, если они есть.
- Комментарии должны объяснять не только действие кода, но и причину выбранного решения, ограничения и последствия нарушения инвариантов.

#### Критические алгоритмы

Пошаговые русские комментарии обязательны в следующих местах:

- разбор raw lines и spans;
- decode/encode escape-последовательностей;
- определение и изменение связанных комментариев;
- выбор записи и разрешение неоднозначности;
- получение и освобождение lock;
- проверка base SHA-256;
- создание и проверка backup/metadata;
- подготовка candidate и post-check;
- порядок `fsync`, `rename` и directory sync;
- сохранение UID/GID/mode/xattrs/security context;
- переходы транзакции и automatic rollback;
- классификация ошибок и выбор exit code;
- обработка частичных и повторных сбоев.

Каждый неочевидный порядок операций должен содержать объяснение, почему именно такой порядок безопасен.

#### Тесты и fixtures

- Каждый тест должен иметь русское описание проверяемого сценария и ожидаемого результата.
- Table-driven cases содержат пояснения к неочевидным входным данным и ожиданиям.
- Fault injection сопровождается комментарием о моделируемой точке сбоя и проверяемой гарантии.
- Назначение неочевидных golden/fuzz fixtures описывается в рядом расположенном комментарии или сопроводительном русском README в `testdata`.
- Комментарий должен помогать понять, какую регрессию обнаружит тест.

#### Конфигурация, сценарии и CI

- Shell-скрипты, Dockerfiles, GitHub Actions и другие сценарии комментируются по файлам, секциям и неочевидным командам.
- YAML-файлы содержат русские пояснения к назначению секций и параметров, если синтаксис допускает комментарии.
- Для каждого примера конфигурации описываются назначение, безопасные значения и возможные побочные эффекты.
- Команды сборки, privileged/VM jobs и обработка секретов должны иметь отдельные пояснения.

#### Форматы без комментариев

- В JSON и других форматах, где комментарии не поддерживаются, синтаксис не должен нарушаться ради комментариев.
- Для таких файлов создаются сопроводительные русские пояснения в `docs`, соседнем README либо поддерживаемых полях `description`.
- Sidecar metadata и machine output документируются через русские schema description без изменения стабильных machine-readable ключей.

#### Поддержка актуальности

- При любом изменении поведения одновременно обновляются затронутые комментарии.
- Устаревший комментарий считается дефектом реализации.
- Комментарии не должны быть формальными или противоречить коду; максимальность достигается полнотой объяснения поведения и ограничений.
- Проверка полноты комментариев включается в code review и приёмку каждого пункта этапа.

## 5. Требования к parser и модели документа

### 5.1. Типы строк

Parser должен различать:

1. Активную запись.
2. Закомментированную запись.
3. Обычный комментарий.
4. Пустую строку.
5. Некорректную строку с сохранением исходного текста и диагностикой.

Некорректная строка не должна молча превращаться в комментарий или удаляться.

### 5.2. Побайтовое сохранение

Обязательные инварианты:

- `Parse(data).Serialize()` возвращает данные, идентичные `data`, если операций редактирования не было.
- Сохраняются LF, CRLF и отсутствие завершающего line ending.
- Сохраняются смешанные line endings как исходные данные, без автоматической нормализации.
- Сохраняются пробелы, табуляция, пустые строки и порядок узлов.
- Изменение одной записи не переформатирует другие записи.
- Удаление записи не удаляет соседние самостоятельные комментарии.
- Операция, не меняющая документ, не создаёт backup и не перезаписывает файл.

### 5.3. Поля записи

- Обязательные первые четыре поля: source, mount point, FS type, options.
- Пятое и шестое поля (`dump`, `pass`) могут отсутствовать в существующей записи.
- Новая запись по умолчанию сериализуется со всеми шестью полями.
- Поля разделяются пробелами и/или табуляцией.
- Исходное и декодированное значения полей хранятся раздельно.
- При редактировании заменяется только диапазон соответствующего поля и при необходимости минимально связанный separator.
- Неизменённые optional-поля не добавляются автоматически к существующей записи.

### 5.4. Экранирование

Минимально обязательны:

- `\040` — пробел;
- `\011` — табуляция;
- `\134` — обратная косая черта.

Дополнительные формы проверяются на совместимость с используемой версией libmount/util-linux.

Требования:

- decode используется для сравнения селекторов и валидации;
- raw value используется для round-trip и diff;
- неизвестная escape-последовательность сохраняется и получает диагностику по правилам совместимости;
- NUL и неэкранированный перевод строки внутри поля являются ошибкой;
- serializer новых значений должен экранировать пробелы, табуляции и backslash совместимым способом.

### 5.5. Комментарии

- `comment` добавляет `# ` к одной активной записи.
- `uncomment` снимает только один префикс комментария у строки, которая после этого распознаётся как запись.
- Обычный текстовый комментарий не включается в список записей только из-за количества слов.
- При неоднозначности строка не раскомментируется автоматически.
- Непрерывный блок непосредственно перед записью может быть связанным комментарием.
- Пустая строка разрывает связь комментария и записи.
- Привязка должна быть консервативной: при сомнении комментарий сохраняется как самостоятельный.
- `--comment` редактирует связанный блок, не затрагивая заголовок файла.
- `--clear-comment` не должен удалять произвольный заголовок или отделённый пустой строкой текст.

### 5.6. Хвостовой текст

- Поведение trailing comments определяется совместимыми тестами с libmount/util-linux.
- До подтверждения семантики хвостовой текст сохраняется как raw data.
- Parser не должен отбрасывать текст после распознанных полей.
- При изменении полей хвостовой текст сохраняется, если сама операция явно его не меняет.

### 5.7. Создание новой записи

- Новая запись добавляется в конец документа.
- Если файл не пуст и не заканчивается line ending, перед новой записью добавляется один line ending.
- Для новой записи используется преобладающий line ending документа; при его отсутствии — LF.
- Новые поля разделяются табуляцией.
- Значения `dump` и `pass` по умолчанию для `add`: `0` и `0`, если пользователь не задал иное.

## 6. Валидация

### 6.1. Severity

| Уровень | Значение | Влияние на сохранение |
|---------|----------|-----------------------|
| `error` | Документ или операция однозначно недопустимы | Сохранение запрещено |
| `warning` | Потенциально опасная или зависимая от среды конфигурация | Разрешено после отображения и подтверждения |
| `info` | Пояснение или нестандартная настройка | Не блокирует |

Каждая диагностика содержит:

- стабильный код;
- severity;
- физический номер строки, если применимо;
- имя/номер поля;
- исходное значение, если безопасно;
- локализованное сообщение;
- необязательные структурированные параметры.

### 6.2. Минимальный набор проверок

- Достаточное количество полей.
- Корректность разделителей.
- Экранирование и управляющие символы.
- Непустые обязательные поля.
- Абсолютная точка монтирования, кроме документированных специальных случаев.
- `none` для swap в соответствии с целевой системой.
- Неотрицательные десятичные `dump` и `pass`.
- Типичные значения `dump`: 0/1; `pass`: 0/1/2.
- Нестандартные неотрицательные `dump`/`pass` — warning, если синтаксис допустим.
- Повторяющиеся устройства и mount points.
- Конфликтующие и повторяющиеся опции.
- Пустые элементы в списке опций.
- Специальные предупреждения для `/`, `/boot`, `/boot/efi`, `/usr` и swap.
- Синтаксическая допустимость source: UUID/LABEL/PARTUUID/PARTLABEL, device path, network source, pseudo FS.
- Доступность FS type и mount helper как проверка среды.
- Наличие устройства и mount point как проверка среды.
- `noauto`, `nofail`, `_netdev`, bind, network и swap.

### 6.3. FS type и options

- Встроенный список типов используется для подсказок и диагностики, не как исчерпывающий whitelist.
- Неизвестный FS type не является автоматической ошибкой parser.
- `bind` обрабатывается как опция, не как FS type.
- `smbfs` получает предупреждение об устаревшести.
- Неизвестная опция по умолчанию вызывает warning.
- Для `ro,rw`, `auto,noauto` и аналогичных пар учитывается documented last-wins, если применимо.
- Очевидно пустые или повреждённые опции являются ошибкой.
- Программа не заявляет проверку всех возможных kernel/helper-опций.

### 6.4. Online и offline

Обычный режим:

- внутренние проверки;
- доступные проверки устройств, mount points и helpers;
- `findmnt --verify --tab-file`.

`--offline`:

- отключает требование фактического наличия внешних устройств, сетевых ресурсов и mount helpers;
- сохраняет parser и внутренние синтаксические проверки;
- не превращает malformed entry в валидную;
- не отменяет `findmnt --verify` перед обычным сохранением.

### 6.5. `findmnt`

Команда проверки:

```bash
findmnt --verify --tab-file <path>
```

Требования:

- До записи проверяется candidate, а не оригинал.
- После записи проверяется фактический target.
- `validate` возвращает внутренние и внешние диагностики в единой модели.
- `verify-mount` выполняет статическую проверку и ничего не монтирует.
- Ненулевой exit code, stdout и stderr сохраняются для диагностики.
- Классификация warning/error не основывается только на ненулевом коде без анализа результата.
- Для парсинга сообщений устанавливается `LC_ALL=C`.
- Правила классификации покрываются fixtures для поддерживаемых версий util-linux.
- Таймаут и невозможность запуска — ошибка внешней утилиты.
- При сохранении error после записи вызывает automatic rollback.
- Warning после записи отображается, но сам по себе rollback не вызывает.

## 7. Адаптер внешних утилит

На первом этапе адаптер обязателен только для `findmnt`, но интерфейс не должен препятствовать добавлению `blkid` и `lsblk` позднее.

Требования:

- Запуск через `exec.CommandContext` без shell.
- Только явный argv, без конкатенации командной строки.
- Поиск исполняемого файла в `/usr/bin`, `/bin`, `/usr/sbin`, `/sbin`.
- Текущий каталог и пользовательский `PATH` не имеют приоритета.
- В результирующем запуске используется абсолютный путь к утилите.
- Для внутреннего разбора `LC_ALL=C`.
- Есть timeout и отмена по context.
- Ограничивается размер сохраняемых stdout/stderr; превышение диагностируется.
- Возвращаются exit code, stdout, stderr, duration и признак timeout.
- Секреты из аргументов и вывода не попадают в журнал без redaction.
- Отсутствие `findmnt` не мешает `--help`, `--version` и операциям, не требующим проверки/записи.

## 8. Блокировка и контроль версии

### 8.1. Lock-файл

Для изменений используется отдельный lock-файл, не `/etc/fstab`.

Системный target:

```text
/run/lock/fstab-edit/<sha256-canonical-target-path>.lock
```

Непривилегированный target:

```text
$XDG_RUNTIME_DIR/fstab-edit/<sha256-canonical-target-path>.lock
```

Если `XDG_RUNTIME_DIR` недоступен, используется приватный пользовательский runtime-каталог с проверкой владельца и режима `0700`. Общий world-writable каталог без защиты не допускается.

Требования:

- Канонический абсолютный путь вычисляется до выбора lock.
- Lock-каталог создаётся с ограниченными правами.
- Lock-файл не является символической ссылкой.
- Используется эксклюзивный `flock`.
- Есть timeout ожидания блокировки и понятная ошибка.
- Lock удерживается до завершения проверки, backup, записи, post-check и возможного rollback.
- Lock не удерживается во время интерактивного ожидания пользователя.
- Read-only команды не создают административные lock-файлы.

### 8.2. Base hash

- При первоначальном чтении вычисляется SHA-256 содержимого.
- Diff и подтверждение строятся относительно этой версии.
- После получения lock target читается повторно.
- Если SHA-256 изменился, операция завершается кодом конфликта.
- Программа не перезаписывает новую версию и не пытается автоматически объединять изменения.
- Для повторной операции пользователь заново загружает файл и проверяет diff.

## 9. Транзакция записи

### 9.1. Общая последовательность

1. Прочитать target как regular file.
2. Вычислить base SHA-256.
3. Выполнить parser и построить candidate в памяти.
4. Если документ не изменился, завершиться без backup/write.
5. Выполнить внутреннюю проверку candidate.
6. Показать diff, диагностики и получить подтверждение, если требуется.
7. Получить exclusive lock.
8. Повторно прочитать target и сравнить SHA-256 с base.
9. Создать безопасный candidate-файл.
10. Выполнить `findmnt --verify --tab-file <candidate>`.
11. При error удалить временные файлы, освободить lock и не менять target.
12. Проверить возможность записи обязательного журнала.
13. Создать backup исходного target и sidecar metadata.
14. Выполнить `fsync` backup и metadata.
15. Проверить backup чтением и SHA-256.
16. Создать финальный temporary file в каталоге target.
17. Записать candidate, применить metadata оригинала и выполнить `fsync`.
18. Атомарно заменить target через `rename`.
19. Выполнить `fsync` родительского каталога.
20. Повторно прочитать target и проверить ожидаемый SHA-256.
21. Выполнить `findmnt --verify --tab-file <target>`.
22. При post-write error восстановить backup именно текущей транзакции.
23. Выполнить разрешённую ротацию после завершения операции.
24. Записать результат в журнал.
25. Удалить temporary files и освободить lock.

### 9.2. Атомарная запись

- Temporary file создаётся в том же каталоге и на той же ФС, что target.
- Имя уникально, создание выполняется безопасно с `O_EXCL`.
- Начальный режим temporary file ограничен; до rename применяются требуемые metadata.
- Перед `rename` выполняется `fsync` файла.
- После `rename` выполняется `fsync` каталога.
- Запись не выполняется поверх symlink, FIFO, socket, device или каталога.
- Сохраняются UID, GID, mode и доступные xattrs/security context.
- Если metadata системного target не могут быть безопасно сохранены, replace не выполняется.
- Ошибка cleanup не должна скрывать первичную ошибку транзакции.

### 9.3. SELinux и AppArmor

- Программа не изменяет политики.
- Root не считается обходом MAC.
- Доступные security xattrs и контекст оригинала сохраняются.
- `EACCES` и `EPERM` диагностируются с указанием операции и пути.
- Ошибка сохранения security context до replace прерывает транзакцию.

### 9.4. Automatic rollback

- Вызывается при ошибке после replace, включая несовпадение expected hash и post-check error.
- Использует backup, созданный на шаге текущей транзакции.
- Не ищет повторно «последний» backup.
- Проверяет SHA-256 backup перед восстановлением.
- Восстановление выполняется атомарно и с `fsync`.
- Результат rollback отражается в выводе и журнале.
- Если rollback тоже failed:
  - возвращается exit code 7;
  - сообщается первичная ошибка и ошибка rollback;
  - выводятся пути target, backup, metadata и log;
  - временные диагностические данные по возможности сохраняются;
  - бесконечных повторов записи нет.

### 9.5. Dry run

`--dry-run`:

- не меняет target;
- не создаёт backup, metadata, lock и log;
- не выполняет rotation;
- допускает временный candidate в приватном каталоге;
- удаляет временные файлы;
- показывает unified diff и диагностики;
- не требует `--yes`;
- не выполняет реальные монтирования.

## 10. Backup и rollback

### 10.1. Backup ID и файлы

Формат ID в UTC:

```text
YYYY-MM-DD_HH-MM-SS.nnnnnnnnnZ
```

Пример:

```text
fstab.bak.2026-11-18_15-30-45.123456789Z
```

Sidecar:

```text
fstab.bak.2026-11-18_15-30-45.123456789Z.json
```

Требования:

- Backup размещается рядом с target по умолчанию.
- `--backup-dir` и `backup.dir` переопределяют каталог.
- Prefix по умолчанию `fstab.bak`.
- При коллизии добавляется числовой суффикс.
- Создание использует `O_EXCL`, symlink не принимается.
- Backup data создаётся с режимом `0600`.
- Sidecar также недоступен посторонним на запись.
- Backup считается готовым только после записи, `fsync` и проверки SHA-256.

### 10.2. Metadata schema

Минимальные поля:

- `schema_version`;
- `backup_id`;
- `created_at` в UTC;
- `source_path`;
- `source_sha256`;
- `backup_sha256`;
- `uid`;
- `gid`;
- `mode`;
- `operation`;
- `program_version`;
- результат доступной исходной проверки.

Operation:

- `before-add`;
- `before-edit`;
- `before-delete`;
- `before-comment`;
- `before-uncomment`;
- `before-rollback`;
- `manual`.

Backup гарантирует восстановление байтов, но metadata не должна молча объявлять исходник работоспособным.

### 10.3. Rotation

- Default `keep`: 10.
- Rotation применяется отдельно к canonical target + prefix.
- Запускается только после завершения операции.
- Не удаляет чужие файлы, symlink и копии другого target.
- Не удаляет backup без корректной идентификации как собственной копии программы.
- Не удаляет выбранную для rollback копию.
- Не удаляет копии аварийной/незавершённой операции.
- Ошибка rotation после успешной записи сообщается отдельно и не должна молча откатывать уже успешное изменение.

### 10.4. Ручной backup

- Создаёт data + metadata и проверяет целостность.
- Не изменяет target.
- Не требует подтверждения изменения target.
- Выводит backup ID и пути.
- Поддерживает `--dry-run` без создания файлов.

### 10.5. Ручной rollback

```bash
fstab-edit rollback
fstab-edit rollback --restore=<backup-id>
```

Последовательность:

1. Найти backup до создания safety copy.
2. Проверить принадлежность target, metadata и SHA-256.
3. Показать diff target → selected backup.
4. Получить подтверждение.
5. Создать safety copy текущего target с operation `before-rollback`.
6. Атомарно восстановить выбранный backup.
7. Выполнить post-check и сообщить результат.
8. Не выбирать повторно последний backup после safety copy.

`rollback --dry-run` только выбирает/проверяет копию и показывает diff.

## 11. CLI

### 11.1. Команды и назначение

| Команда | Результат |
|---------|-----------|
| `list` | Показывает активные и закомментированные записи |
| `add` | Добавляет новую запись |
| `edit` | Изменяет выбранные поля/comment |
| `delete` | Удаляет запись |
| `comment` | Комментирует активную запись |
| `uncomment` | Включает закомментированную запись |
| `validate` | Проверяет документ и среду |
| `verify-mount` | Выполняет статический `findmnt --verify` |
| `backup` | Создаёт ручную копию |
| `rollback` | Восстанавливает выбранную копию |

### 11.2. Глобальные флаги

| Флаг | Требование |
|------|------------|
| `--file=<path>` | Альтернативный target |
| `--dry-run` | Diff/check без постоянных изменений |
| `--yes`, `-y` | Подтверждение допустимой операции |
| `--output=<format>`, `-o` | `table`, `json`, `csv`, `tsv` |
| `--log-level=<level>` | `debug`, `info`, `warn`, `error` |
| `--verbose`, `-v` | Дополнительная диагностика |
| `--quiet`, `-q` | Подавление обычного stdout |
| `--backup-dir=<path>` | Каталог backup |
| `--offline` | Отключить проверки наличия внешних ресурсов |
| `--lang=ru|en` | Язык сообщений |
| `--config=<path>` | Явный config |
| `--help`, `-h` | Справка |
| `--version` | Версия |

Правила:

- `--verbose` и `--quiet` несовместимы.
- `--quiet` не скрывает errors.
- `--help` и `--version` не читают target и не запускают `findmnt`.
- Значения флагов имеют приоритет над env и YAML.
- Неизвестный format/level/lang — usage error.

### 11.3. Селекторы записей

Поддерживаются positional `<id>`:

- физический номер строки;
- mount point;
- source/device.

И явные селекторы:

```text
--line <n>
--mount-point <path>
--device <source>
```

Правила:

- Используется ровно один способ выбора записи.
- Positional ID и явный selector одновременно запрещены.
- Явные selectors взаимоисключающи.
- Сравнение полное, по decoded value, не substring.
- Physical line нумеруется с 1 и учитывает пустые/comment lines.
- Symlink resolution не используется для идентичности mount point.
- Несколько совпадений — ambiguity error.
- Interactive выбор допускается только при TTY и без `--yes`.
- Non-interactive ambiguity возвращает код 8 и список кандидатов.
- `--yes` никогда не выбирает произвольный кандидат.
- `comment` требует активную запись, `uncomment` — закомментированную.

### 11.4. Add/edit flags

```text
--device <source>
--mount <path>
--type <fstype>
--options <list>
--dump <n>
--pass <n>
--comment <text>
--clear-comment
--unset-dump
--unset-pass
```

`add`:

- обязательны `--device`, `--mount`, `--type`, `--options`;
- `--dump` default 0;
- `--pass` default 0;
- допускается `--comment`;
- edit-only/unset flags не применяются к отсутствующей записи.

`edit`:

- требуется selector;
- должен быть задан хотя бы один изменяющий флаг;
- меняются только явно указанные поля;
- обязательное поле нельзя сделать пустым;
- `--comment` и `--clear-comment` несовместимы;
- `--unset-dump`/`--unset-pass` удаляют optional-поле, сохраняя остальную запись;
- если фактических изменений нет, backup/write не выполняются.

### 11.5. List

- Включает active и commented entries.
- Не включает обычные comments и blank lines как записи.
- Показывает physical line и state.
- Table содержит source, mount point, FS type, options, dump, pass и краткий статус.
- JSON/CSV/TSV содержат raw и decoded поля согласно schema.
- Отсутствующие optional-поля представляются явно, а не подменяются значениями по умолчанию.

### 11.6. Подтверждения

`[y/N]` требуется для:

- `add`;
- `edit`;
- `delete`;
- `comment`;
- `uncomment`;
- `rollback`.

Правила:

- До prompt показываются diff и warnings.
- Без TTY изменяющая команда требует `--yes`.
- Ответ по умолчанию — No.
- `--yes` не обходит parse error, validation error, lock conflict, ambiguity или отсутствие прав.
- Для critical entries показывается дополнительное warning.
- Ручной backup не изменяет target и не требует general mutation prompt.

### 11.7. Diff

- Используется unified diff.
- В заголовках различимы original и candidate.
- Неизменённые строки не переформатируются ради diff.
- При machine output diff является полем структуры или отдельным документированным представлением.
- Секретные option values маскируются в log; в пользовательском diff показываются только если это безопасно и необходимо для подтверждения.

### 11.8. Вывод и ошибки

- Обычные данные — stdout.
- Диагностика — stderr, кроме явно документированного structured error protocol.
- Машиночитаемый stdout не смешивается с log/progress.
- Table предназначен для людей, не для скриптового parsing.
- Цвет не используется в JSON/CSV/TSV.
- `--quiet` не меняет exit code.

### 11.9. JSON

Корневой объект содержит `schema_version` со значением `1` для первой стабильной схемы.

Минимальные данные записи:

- `line`;
- `state`;
- `raw` и `decoded` для шести полей;
- наличие optional-полей;
- `comment`;
- `diagnostics`.

Результат mutation содержит:

- `operation`;
- `changed`;
- `dry_run`;
- `target`;
- `diff`;
- `diagnostics`;
- `backup_id`, если создан;
- `rollback` и его результат, если выполнялся.

Обратно несовместимые изменения требуют новой `schema_version`.

### 11.10. CSV/TSV

- UTF-8.
- Первая строка — стабильные имена колонок.
- CSV quoting по стандартным правилам с запятой, кавычкой и newline.
- TSV корректно экранирует tab/newline или использует документированную замену без потери обратимости.
- Physical line и state обязательны.
- Raw/decoded поля не смешиваются в одну неоднозначную колонку.
- Diagnostics имеют отдельный документированный формат, не добавляются как псевдозаписи fstab.

### 11.11. Exit codes

| Код | Значение |
|-----|----------|
| 0 | Успех; warnings допустимы |
| 1 | Validation/check завершился error |
| 2 | CLI usage error |
| 3 | Недостаточно прав |
| 4 | Lock timeout или base hash conflict |
| 5 | External utility error/timeout |
| 6 | I/O, backup, metadata или write error |
| 7 | Critical rollback failure |
| 8 | Ambiguous entry selector |

Если несколько ошибок, приоритет должен быть документирован. Critical rollback failure имеет наивысший приоритет. Первичная ошибка не теряется при cleanup/logging errors.

### 11.12. Примеры

```bash
fstab-edit list
fstab-edit list -o json

fstab-edit add --device UUID=abc-123 --mount /mnt/data --type ext4 \
  --options defaults,noatime --dump 0 --pass 2

fstab-edit edit --mount-point /mnt/data --options defaults,noatime,nofail
fstab-edit delete --mount-point /mnt/data --yes

fstab-edit comment --line 12
fstab-edit uncomment --line 12

fstab-edit validate --file ./fstab.test --offline
fstab-edit verify-mount --file ./fstab.test

fstab-edit backup --file ./fstab.test
fstab-edit rollback --dry-run
fstab-edit rollback --restore=2026-11-18_15-30-45.123456789Z
```

## 12. Права и безопасность файлов

### 12.1. Root

- Read-only операции не требуют root сами по себе.
- Изменение `/etc/fstab` требует effective UID 0.
- Альтернативный `--file` редактируется с правами текущего пользователя.
- Root требуется только при фактической необходимости.
- Подсказка `sudo` выводится только для операции, которой действительно не хватает привилегий.
- Read-only команды не создают `/var/log/fstab-edit.log`, `/run/lock/...` и другие административные файлы.

### 12.2. Проверки путей

- Target должен быть regular file.
- Symlink target отклоняется.
- Backup, metadata, config и log проверяются на symlink/подмену.
- Права и владелец security-sensitive файлов проверяются до использования.
- Относительный target преобразуется в абсолютный путь.
- Программа не следует по небезопасному пути только потому, что запущена от root.
- Temporary files имеют ограниченные права и удаляются при штатном завершении.

## 13. Конфигурация

### 13.1. Приоритеты

От высшего к низшему:

1. CLI flags.
2. `FSTAB_EDIT_*`.
3. User YAML.
4. System YAML.
5. Defaults.

YAML объединяются по ключам; отсутствующий ключ не затирает значение низшего уровня.

Пути:

```text
/etc/fstab-edit/config.yaml
~/.config/fstab-edit/config.yaml
```

### 13.2. Безопасность config

- Для root home определяется по effective UID, не по непроверенному `HOME`.
- Config непривилегированного `SUDO_USER` автоматически root-процессом не загружается.
- Symlink config отклоняется.
- Root отклоняет user config, не принадлежащий root или доступный group/others на запись.
- System config принадлежит root и недоступен непривилегированным пользователям на запись.
- `--config` не отключает ownership/mode checks.
- Небезопасный config вызывает явную ошибку.

### 13.3. Минимальная схема

```yaml
fstab_path: /etc/fstab

backup:
  dir: /etc
  prefix: fstab.bak
  keep: 10

log:
  file: /var/log/fstab-edit.log
  level: info
  max_size_mb: 10
  keep: 5

tui:
  theme: dark
```

Ключ `tui` на первом этапе может сохраняться для совместимости, но не влияет на CLI.

### 13.4. Переменные окружения

Минимально поддерживаются соответствия для:

- `FSTAB_EDIT_FILE` / документированный эквивалент `fstab_path`;
- `FSTAB_EDIT_BACKUP_DIR`;
- `FSTAB_EDIT_LOG_LEVEL`;
- `FSTAB_EDIT_LANG`;
- `FSTAB_EDIT_OUTPUT`.

Окончательные имена должны быть единообразны в help, man, README и коде. Неизвестные `FSTAB_EDIT_*` не должны молча менять поведение.

## 14. Журналирование

- Default path: `/var/log/fstab-edit.log`.
- Формат: JSON Lines, одно событие на строку.
- Коды событий и operations не локализуются.
- Timestamp: ISO 8601.
- Поля: severity, real/effective UID, доступные проверенные sudo-сведения, operation, target, backup ID, result, error code, duration.
- Для mutation сохраняются old/new values с escaped newlines и redaction.
- Passwords, tokens, secrets и чувствительные URL components маскируются.
- Default rotation: 10 МиБ, пять архивов.
- Systemd journal на первом этапе не используется.
- Read-only и dry-run не создают файловый журнал.
- Перед mutation проверяется доступность log; если log недоступен до точки изменения, target не меняется.
- Если log failed после replace, это не должно мешать обязательному rollback.
- Первичная write/rollback error не заменяется logging error.

## 15. Локализация

- Языки: RU и EN.
- Приоритет выбора: `--lang`, `LC_ALL`/`LANG`, English fallback.
- Help, errors, warnings, prompts и подтверждения переводятся.
- Exit codes, diagnostic codes, JSON keys, enum values и log operation codes не переводятся.
- Отсутствующий перевод использует English и не приводит к panic.
- Строки не собираются конкатенацией, если это мешает корректному переводу.
- Подтверждение принимает документированные localized yes/no forms и безопасно по умолчанию выбирает No.

## 16. Тестирование

### 16.1. Общие требования

- Тесты размещаются по стандартным Go-соглашениям рядом с пакетами и в `testdata`.
- Общее покрытие: не менее 80%.
- Критические writer/backup/rollback сценарии обязательны независимо от общего процента.
- Тесты по умолчанию не требуют root.
- Внешние команды подменяются fake/runner в unit/integration tests.
- Реальные privileged/destructive tests выполняются только в изолированной VM.
- Тесты не используют реальный `/etc/fstab`.

### 16.2. Parser tests

Обязательны:

- Пустой файл.
- Только comments/blank lines.
- Четыре, пять и шесть полей.
- Active/commented entries.
- Spaces/tabs и смешанные separators.
- LF, CRLF, mixed endings, no final newline.
- `\040`, `\011`, `\134`.
- Escaped mount point и source.
- Unicode labels/comments.
- Некорректные escape и control characters.
- Trailing text/comments.
- Associated и standalone comments.
- Duplicate mount/source.
- No-op byte equality.
- Minimal diff при изменении одного поля.
- Добавление к файлу без final newline.
- `unset-dump`/`unset-pass`.
- Консервативный uncomment.

### 16.3. Golden и round-trip

- Для каждого fixture сохраняется ожидаемый результат операции.
- Для неизменённых fixtures проверяется побайтовое равенство.
- Отдельно проверяется, что затронуты только разрешённые строки.
- Golden updates не выполняются автоматически без явной команды разработчика.

### 16.4. Fuzz

Fuzz targets как минимум для:

- Parse → Serialize без mutation.
- Decode/encode полей.
- Комментирования/раскомментирования.
- Выбора записи по decoded selectors.

Инварианты:

- Нет panic.
- Нет бесконечного цикла.
- No-op round-trip не теряет данные.
- Ошибка parser не приводит к частично модифицированному документу.

### 16.5. Writer/backup fault injection

Обязательные сценарии:

- Lock timeout.
- Внешнее изменение target после base read.
- Нехватка места.
- Read-only FS.
- Candidate write failure.
- Backup create/write/fsync failure.
- Metadata create/write/fsync failure.
- Backup SHA mismatch.
- Target metadata preservation failure.
- Failure до rename.
- Failure после rename.
- Parent directory fsync failure, если поддерживается тестовой абстракцией.
- `findmnt` timeout.
- `findmnt` pre-check error.
- Post-write expected hash mismatch.
- `findmnt` post-check error.
- Successful automatic rollback.
- Rollback failure и exit code 7.
- Log unavailable до mutation.
- Log failure после replace.
- Cleanup failure без потери первичной ошибки.
- Rotation не удаляет чужие/активные/emergency backups.

### 16.6. CLI E2E

Для каждой команды проверяются:

- Help.
- Обязательные аргументы.
- Usage errors и exit 2.
- Dry-run без изменений.
- Confirmation Yes/No.
- Non-TTY без `--yes`.
- `--yes`.
- Selector ambiguity и exit 8.
- Base conflict и exit 4.
- Table/JSON/CSV/TSV.
- stdout/stderr separation.
- `--quiet`/`--verbose`.
- RU/EN.
- Exit codes 0–8 в доступных сценариях.
- No-op без backup.
- Реальные операции только с temporary `--file` и temporary backup/log paths.

### 16.7. VM-тесты этапа

В изолированных VM:

- Изменение тестового системного `fstab` и rollback.
- Сохранение UID/GID/mode.
- SELinux enforcing в хотя бы одной поддерживаемой среде.
- Backup и аварийное восстановление.
- Контролируемые сценарии `/`, `/boot`, `/home`, swap, `nofail`, `noauto`, `_netdev`, bind.
- Перезагрузка после принятых безопасных изменений.
- Проверка, что failed transaction восстанавливает исходные байты.

Контейнерные CLI-тесты не засчитываются как boot validation.

### 16.8. Команды проверки

```bash
go test ./... -v
go test -race ./...
go test ./... -cover
golangci-lint run
CGO_ENABLED=0 go build -trimpath -o fstab-edit .
```

Release build дополнительно проверяется на статическую компоновку и запуск `--help`, `--version`, `list --file <fixture>`.

## 20. Критерии завершения первого этапа

Этап считается завершённым только при выполнении всех условий:

### 20.1. Parser и операции

- [ ] No-op Parse/Serialize побайтово сохраняет документ.
- [ ] Изменение записи не переформатирует остальные строки.
- [ ] Поддержаны active/commented entries, comments, blanks и optional dump/pass.
- [ ] Экранирование и line endings покрыты тестами.
- [ ] Все девять основных CLI-команд реализованы.
- [ ] No-op mutation не создаёт backup и не пишет target.

### 20.2. Проверка и CLI

- [ ] Внутренние diagnostics имеют stable codes и severity.
- [ ] Candidate проходит `findmnt --verify` до записи.
- [ ] `verify-mount` не монтирует ресурсы.
- [ ] Table/JSON/CSV/TSV соответствуют документации.
- [ ] Exit codes 0–8 реализованы и протестированы.
- [ ] Non-interactive ambiguity не разрешается `--yes`.
- [ ] Dry-run не создаёт target/backup/lock/log изменений.

### 20.3. Безопасная запись

- [ ] Используется отдельный stable lock-файл.
- [ ] Base SHA-256 предотвращает overwrite внешних изменений.
- [ ] Перед записью создан и проверен backup + metadata.
- [ ] Replace атомарен, выполнены требуемые `fsync`.
- [ ] Сохраняются права, владелец и доступный security context.
- [ ] Post-write error вызывает rollback копии текущей транзакции.
- [ ] Rollback failure возвращает 7 и пути для ручного recovery.
- [ ] Реальное монтирование не вызывается.

### 20.4. Backup и rollback

- [ ] Backup ID уникален и однозначен по UTC.
- [ ] SHA-256 backup проверяется.
- [ ] Manual rollback выбирает цель до safety copy.
- [ ] Rotation ограничена target/prefix и не удаляет защищённые копии.
- [ ] Повреждённый исходник не представляется гарантированно работоспособным.

### 20.5. Конфигурация и эксплуатация

- [ ] Приоритеты CLI/env/user/system/defaults соблюдены.

- [ ] Read-only команды не требуют root без необходимости.

- [ ] Все обязательные fault-injection сценарии проходят.

## 21. Ограничения гарантий

Первый этап не гарантирует невозможность любой загрузочной проблемы.

Гарантируются только проверяемые свойства:

- backup успешно создан и проверен до записи;
- candidate проверен до replace;
- внешняя версия не перезаписывается незаметно;
- replace атомарен;
- post-write error инициирует заданный rollback;
- двойной сбой явно диагностируется;
- резервная копия восстанавливает исходные байты.

Исходная конфигурация могла быть повреждена до запуска программы. `findmnt` не доказывает все boot/network/systemd-сценарии. Для принятых критичных изменений остаются обязательными изолированные VM и фактические boot-тесты.
